## Problem Statement

BetaRouter currently has two credential paths:

- Organization-owned provider keys, managed through the customer dashboard and used in `api-keys` or `hybrid` mode.
- Operator-owned provider credentials, supplied as `LLM_*` environment variables and used for `credits` traffic and `hybrid` fallback.

The operator path cannot be managed from the admin dashboard. Adding a channel requires terminal access, editing `.env.production`, changing Compose for optional settings such as a base URL, and recreating the application container. This prevents BetaRouter from operating upstream channels as a normal platform function.

## Demand Evidence

The operator explicitly requested: “Build this interface into admin -> platform providers for me to manage this.” They also require controlled reveal because “sometime need to adjust and verify from admin operation.” This is an immediate production operations need, not a hypothetical feature.

## Status Quo

Platform credentials are read synchronously from process environment variables by gateway routing. Customer BYOK keys are database-backed but organization-scoped and do not serve platform-funded traffic. The admin dashboard can inspect organization provider keys but cannot create, validate, rotate, reveal, disable, or route operator-owned credentials.

## Target User & Narrowest Wedge

The target user is the BetaRouter platform administrator. The narrowest useful version is one admin screen that can:

1. Add an operator-owned provider credential and optional upstream base URL.
2. Validate it before activation.
3. Make it available to `credits` traffic and `hybrid` fallback without a container restart.
4. Mask it by default, reveal it through an explicit audited action, replace it, disable it, and delete it.

## Constraints

- Existing environment credentials must continue working as a deployment/bootstrap fallback.
- Tenant BYOK behavior and organization isolation must not change.
- Plaintext provider tokens must never appear in lists, logs, errors, analytics, URLs, or audit metadata.
- Database backups must contain ciphertext only.
- The root encryption key must remain outside PostgreSQL and outside Git.
- Only accounts present in both the platform `ADMIN_EMAILS` allowlist and the immutable `PLATFORM_ADMIN_USER_IDS` allowlist, with a valid admin session, may manage credentials; tenant enterprise organization roles do not grant access.
- Multiple active credentials for one provider must support deterministic priority and health-aware failover.
- Each database row is one atomic credential configuration; its base URL and provider-specific options travel with that row rather than using environment-list index alignment.
- A failed database/cache dependency must fail closed for database-managed credentials while preserving configured environment fallback.

## Premises

1. Platform credentials are distinct from organization BYOK credentials and must have a separate table and API surface.
2. Database-managed credentials apply only to `credits` mode and the fallback branch of `hybrid` mode.
3. Credentials are encrypted with authenticated encryption before persistence. Versioned 32-byte root keys are provided through `PLATFORM_PROVIDER_ENCRYPTION_KEYS`, and `PLATFORM_PROVIDER_ENCRYPTION_CURRENT_VERSION` selects the write key.
4. Reveal is permitted because the operator requires it, but it is a POST-only, rate-limited and audited endpoint protected by the platform admin allowlist/session boundary. Normal list/detail endpoints never return plaintext.
5. Environment credentials remain supported and are merged after active database credentials so an existing deployment is not broken during migration.
6. Admin mutations become visible to gateway traffic without a process restart through a short-lived shared cache of ciphertext and non-secret metadata with explicit invalidation. Plaintext is decrypted only inside the consuming process and is never serialized into Redis.

## Approaches Considered

### Approach A: Environment Variables Only

Keep `LLM_*` variables as the source of truth and add an admin form that edits deployment configuration. This is the smallest code change, but it couples the web application to host filesystem/process control, requires restarts, has poor auditing, and creates dangerous privilege escalation from the admin API into the Droplet.

### Approach B: Encrypted Database Registry

Store operator credentials in a dedicated table as AES-256-GCM ciphertext. Keep only the root encryption key in the server environment. Add admin CRUD, validation, reveal, status and rotation operations. Resolve active credentials through a shared cached repository and merge environment credentials as fallback.

### Approach C: External Secrets Manager

Use a purpose-built vault and keep only provider metadata in PostgreSQL. This offers stronger separation and mature rotation, but adds a new paid/operational dependency, network failure mode, credential bootstrap path and deployment work that is disproportionate for the current single-Droplet stage.

## Recommended Approach

Approach B is approved. It gives the administrator a normal operational interface without granting the web application arbitrary host configuration privileges. It protects database dumps, keeps environment fallback compatibility, and leaves a future migration path to a cloud vault behind a repository interface.

## Detailed Design

### Data model

Add `platform_provider_credential` with:

- Identity and routing: `id`, `provider`, `name`, `baseUrl`, `options`, `priority`, `status`.
- Encrypted secret envelope: `encryptedToken`, `encryptionIv`, `encryptionAuthTag`, `encryptionKeyVersion`.
- Safe display metadata: `maskedToken`, `tokenFingerprint`.
- Validation: `validationStatus`, `validationMessage`, `lastValidatedAt`.
- Operations: `createdAt`, `createdBy`, `updatedAt`, `updatedBy`, `deletedAt`, `lastUsedAt`, `lastRevealedAt`, `lastRevealedBy`.

Soft deletion preserves audit references. The plaintext token is never stored. Active rows are indexed by `(provider, status, priority)`; active credential names are unique per provider. Token fingerprints use a domain-separated HMAC-SHA-256 keyed independently from ciphertext encryption, are indexed for duplicate detection, are never displayed, and are never accepted as authentication material or proof of token possession.

Add a separate `platform_audit_log` because the existing audit log requires an organization id. It records platform administrator identity, action, credential id, success/failure, request id, IP metadata and timestamp. Supported actions include create, validate, reveal, rotate, update, activate, deactivate and delete. No secret, ciphertext, IV, authentication tag or raw upstream response is audit metadata.

### Cryptography

- AES-256-GCM with a fresh random 96-bit IV per encryption.
- `PLATFORM_PROVIDER_ENCRYPTION_KEYS` is a versioned key ring outside PostgreSQL, for example `v1:<base64-key>,v2:<base64-key>`, and `PLATFORM_PROVIDER_ENCRYPTION_CURRENT_VERSION` selects the write key. Every configured key must decode to exactly 32 bytes.
- Provider id and credential id are authenticated as additional authenticated data so ciphertext cannot be moved between records unnoticed.
- Decryption errors return a generic operational failure and never include secret material.
- New writes use the current key version; reads accept every configured version. This permits safe master-key rotation by adding a new version, switching writes, re-encrypting rows and only then removing the old key.

### Admin API

- `GET /admin/platform-providers`: masked list with validation/status metadata.
- `POST /admin/platform-providers`: validate, encrypt and create.
- `PATCH /admin/platform-providers/{id}`: update metadata/status or replace the token.
- `POST /admin/platform-providers/{id}/validate`: decrypt server-side and validate upstream.
- `POST /admin/platform-providers/{id}/reveal`: return plaintext only after platform-admin authorization and successful audit recording.
- `DELETE /admin/platform-providers/{id}`: soft delete and invalidate runtime cache.

Every create, update, reveal, validation, status change and deletion records an audit event. These routes require both the `ADMIN_EMAILS` platform allowlist and immutable `PLATFORM_ADMIN_USER_IDS` allowlist plus a valid admin session; organization owner/admin roles do not grant access. Reveal is POST-only, requires an exact same-origin request and a login less than 15 minutes old, is rate-limited globally and per credential, and records both attempted and completed outcomes. Reveal responses use `Cache-Control: no-store`, bypass analytics capture, and pass through response/error redaction that removes token-shaped strings.

### Admin interface

Add **Platform Providers** to the main admin sidebar. The page includes:

- Provider cards/table with provider, channel name, masked key, base URL, validation status, active status and last validation time.
- Add/edit dialog with provider-specific settings.
- Validate, activate/deactivate, rotate, reveal and delete actions.
- Reveal requires an explicit confirmation, renders for 30 seconds, and can be hidden immediately.
- Loading, empty, validation error, decrypt/configuration error and success states.
- No secret is persisted in client state beyond the reveal component lifetime.

### Gateway resolution

Introduce an asynchronous platform credential resolver shared by API and gateway processes. Its Redis/SWR layer stores only encrypted rows and non-secret metadata. The consuming process decrypts a selected row immediately before use; decrypted values are never written back to Redis or another serialized cache. Cache reads use explicit `platformProvider:active`, `platformProvider:provider:{provider}` and `platformProvider:list` keys tagged with the platform credential table. Admin mutations go through one repository helper that invalidates the table tag and these query families across processes.

Migrate the existing synchronous `getProviderEnv()` seam to an async `resolvePlatformProviderCredential()` seam. The resolver returns a normalized credential configuration containing token, base URL, row-local options, region, source id and source type. Chat, responses, embeddings, OCR, speech, video, image and moderation paths that currently consume environment credentials must use this seam. Provider/model and regional availability filtering must query the same cached encrypted metadata before final selection, so a database-only provider is not filtered out early.

For `credits` mode, active database credentials are preferred and compatible environment credentials are the final fallback. For `hybrid`, an organization BYOK key remains first; the platform resolver runs only when no organization key exists. Selection uses ascending priority buckets and excludes unhealthy or request-failed credentials. Within the best available bucket, the healthiest credential wins with a deterministic creation-order tie-break. Row-local base URL/options/region are returned with the selected token. Environment credentials remain a final virtual priority bucket and retain their existing comma-index selection.

Service-tier eligibility, region filtering and retry/failover logic must evaluate both database row metadata and environment configuration. Validation and upstream errors are sanitized before logging, auditing or returning to the admin UI; raw upstream response bodies and token-shaped substrings are never persisted.

If the encryption key ring is missing or invalid, create/update/reveal operations fail closed with a generic configuration error. Database credential resolution also fails closed for affected rows. Environment fallback remains usable only when resolution does not require reading or decrypting a database-managed row; the resolver must never silently skip an active but undecryptable database credential as if it were healthy.

### Compatibility and rollout

1. Add the table/migration and encryption key configuration.
2. Deploy with no database-managed credentials. Existing environment credentials continue serving traffic.
3. Add and validate credentials through Admin.
4. Confirm traffic and health attribution across every gateway surface that previously used environment credential fallback.
5. Remove duplicated provider secrets from `.env.production` only after the database path is verified.

## Open Questions

- Step-up authentication is not currently available in the admin application. Initial reveal protection will use explicit confirmation, the platform admin allowlist/session boundary, same-origin request protection, rate limiting, no-store responses and attempted/completed audit logging. Password/passkey re-authentication remains a follow-up when the auth layer exposes a supported step-up flow.
- External vault integration is intentionally deferred behind the repository boundary.

## Success Criteria

- An authorized admin can add, validate, reveal, rotate, deactivate and delete a platform credential from `admin.betarouter.com`.
- List/detail responses never include plaintext tokens.
- A PostgreSQL dump contains no plaintext provider token.
- Reveal events identify the administrator, credential and timestamp without logging the token.
- A newly activated credential serves `credits` traffic without restarting the container across chat/responses, embeddings, OCR, speech, video, image and moderation surfaces supported by that provider.
- Organization BYOK traffic remains isolated and unchanged.
- Environment-only deployments continue working.
- Unit/integration tests cover encryption/key rotation, authorization, CSRF/same-origin behavior, masking, reveal auditing/rate limiting, validation redaction, cache invalidation, provider/region availability, routing precedence, retry/health behavior and every existing environment-fallback gateway surface.

## Dependencies

- New production `PLATFORM_PROVIDER_ENCRYPTION_KEYS` and `PLATFORM_PROVIDER_ENCRYPTION_CURRENT_VERSION` secrets.
- Existing admin email allowlist, immutable platform-admin user ID allowlist, and session authentication.
- Existing provider definitions, key validation action, audit event service, PostgreSQL and Redis/cache primitives.

## The Assignment

Implement the approved encrypted registry, prove with automated migration/integration tests that persisted rows contain ciphertext only, and add a deployment runbook step for post-deploy production verification across supported gateway surfaces. Production credential creation remains an explicit operator action after deployment.
